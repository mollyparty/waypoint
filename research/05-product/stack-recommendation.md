# Waypoint Technical Stack Recommendation

Version-Timestamp: 2026-07-30 16:45:00 UTC-4

Scope: the recommended architecture and stack for Waypoint's iOS v1, per the locked concept (`research/04-synthesis/concept.md`, DEC-006) and the compliance obligations in `research/01-market/regulatory-compliance.md`. Every external claim carries a source with URL and access date plus a [verified]/[inferred]/[assumption] tag per the playbook. All sources accessed 2026-07-30 unless noted. Prices exclude VAT unless stated; verify pricing again at contract time because vendors change terms.

Executive verdict: self-host the open-source GraphHopper routing engine as the route generation core (it is the only engine that combines a native round-trip primitive with declarative custom cost models under a permissive license), keep the moat data in Postgres plus PostGIS on Supabase, build the app native SwiftUI plus MapKit with our own voice guidance, run coaching inference on-device via Apple's Foundation Models framework, and sell through Apple IAP managed by RevenueCat. Estimated infrastructure cost: roughly $90 per month at MVP, roughly $330 per month at 10k MAU.

## 1. Routing engine (the heart)

### What Waypoint actually needs from a router

1. Loop (round-trip) generation from a single start point at a target distance. This is the hero feature's primitive.
2. Custom cost models that can weight edges by our own data: street-crossing penalties, lighting and populated-path scores, surface preference, elevation preference, heat exposure. The moat is this constraint data, so the engine must accept per-edge custom costs, ideally per request (constraints change per run).
3. Self-hostable, permissive license, operable by one contractor-supported founder.

### Candidate comparison

**Self-hosted OSM engines**

- **GraphHopper (open source)**: Apache 2.0 license, explicitly chosen so companies can embed it in closed-source products. Has a native `round_trip` algorithm ("the route will get you back to where you started", with `round_trip.distance` and `round_trip.seed` parameters) and custom models: JSON rules that adjust edge `speed` and `priority` based on encoded values (road class, surface, and more), submitted per request via POST /route with `ch.disable=true`. Custom models are officially labeled a beta feature. [verified] (GitHub, graphhopper/graphhopper README and license, https://github.com/graphhopper/graphhopper; GraphHopper API docs, round_trip parameters, https://docs.graphhopper.com/openapi/routing/getroute; custom models doc, https://github.com/graphhopper/graphhopper/blob/master/docs/core/custom-models.md; all accessed 2026-07-30)
  - Key implication: Waypoint's proprietary per-edge data (crossing density, lighting score) can be baked into the graph at build time as custom encoded values, then weighted per request through the custom model JSON. Node-level penalties (individual crossings) are not first-class in the JSON custom model language and will likely need a small amount of Java-level customization, which GraphHopper's library architecture supports. [inferred from the custom models documentation, which operates on edge encoded values]
- **Valhalla**: MIT licensed, and the strongest dynamic run-time costing architecture of the set: costing is computed at query time from rich edge attributes (the Sif component), so different route characters need no data rebuild, and `linear_cost_factors` accepts per-request geometries with avoid/prefer factors. But it has no native round-trip primitive: loops must be constructed by placing waypoints manually, and per-edge custom penalties from the request payload beyond `linear_cost_factors` are still an open feature request. [verified] (Valhalla docs, dynamic costing, https://valhalla.github.io/valhalla/concepts/costing/dynamic-costing/; API reference including linear_cost_factors, https://valhalla.github.io/valhalla/api/turn-by-turn/api-reference/; GitHub issue #5699 on per-edge custom penalties, https://github.com/valhalla/valhalla/issues/5699; all accessed 2026-07-30)
- **OpenRouteService (self-hosted)**: has round-trip generation with length, roundness, and randomization controls (the feature description even names jogging as the use case). Self-hosting removes the public API limits. Its backend license was not verified in this pass; treat as unconfirmed before any adoption decision. [verified as to the round-trip feature] (HeiGIT, "Openrouteservice Maps: alternative routes, roundtrips and more", https://heigit.org/openrouteservice-maps-alternative-routes-roundtrips-and-more/, accessed 2026-07-30; license status [assumption] A4)
- **BRouter**: MIT licensed, and the most expressive cost-function system of the set: a scripting language over OSM tags rather than parameter sets ("program the cost function instead of just configuring it"), with elevation awareness built in. But it is designed as an offline Android router; the maintainer states there is no well-documented API for embedding, the community is small (about 664 GitHub stars, 50 contributors), and there is no loop primitive. A source of ideas for our cost functions, not a production server. [verified] (GitHub, abrensch/brouter, https://github.com/abrensch/brouter; BRouter cost functions page, https://brouter.de/brouter/costfunctions.html; API discussion in issue #149, https://github.com/abrensch/brouter/issues/149; all accessed 2026-07-30)

**Hosted APIs**

- **GraphHopper Directions API (cloud)**: free tier 500 credits/day (non-commercial), Basic 69 EUR/month for 5,000 credits/day, Standard 199 EUR/month for 15,000/day, Premium 479 EUR/month for 50,000/day. A round-trip request costs 2 credits. Supports `custom_model` per request. [verified] (GraphHopper pricing, https://www.graphhopper.com/pricing/; plans and credit schedule, https://docs.graphhopper.com/openapi/section/plans-and-rate-limits; both accessed 2026-07-30)
  - The disqualifier: the cloud API weights the encoded values GraphHopper ships. Our proprietary per-edge data (crossings, lighting) cannot be imported into their hosted graph, so the moat cannot run there. [inferred from the custom model documentation, which requires encoded values present in the server-side graph]
- **Mapbox Directions API / Navigation SDK**: Directions API free to 100,000 requests/month then $2.00 per 1,000; Navigation SDK metered-trips model has a free tier of 100 MAU plus 1,000 trips. No loop generation and no custom cost model at all: it routes A to B on Mapbox's profiles. Also a third-party SDK that would need a privacy audit under our compliance posture. [verified as to pricing] (Mapbox pricing, https://www.mapbox.com/pricing, and Navigation SDK pricing docs, https://docs.mapbox.com/ios/navigation/guides/pricing/, accessed 2026-07-30; the "no custom costing" characterization is [inferred] from the absence of any such feature in Mapbox's Directions documentation)
- **Stadia Maps (hosted Valhalla)**: commercial plans at $20, $80 ($80 tier includes 7.5M credits/month), and $250/month (25M credits); standard routing costs 20 credits per request, so the $20 plan covers tens of thousands of route requests. Inherits Valhalla's strengths and its no-native-loop limitation; custom per-edge data cannot be imported into their hosted graph (they do offer bespoke enterprise deployments). Stadia also maintains Ferrostar, an open-source navigation SDK (relevant to section 3). [verified] (Stadia Maps pricing, https://stadiamaps.com/pricing/; credit schedule blog, https://stadiamaps.com/blog/2024-matrix-navigation-credit-updates/; routing product page naming Valhalla and Ferrostar, https://stadiamaps.com/products/routing-navigation/; all accessed 2026-07-30)
- **openrouteservice public API**: free Standard plan, 2,000 directions requests/day, round trips capped at 100 km. Generous, but it is a donation-funded academic service with no SLA, and the plan structure is not built for a commercial product's production traffic. [verified] (openrouteservice plans, https://openrouteservice.org/plans/ (staging mirror content identical), and restrictions, https://openrouteservice.org/restrictions/, accessed 2026-07-30)

### Verdict: self-hosted GraphHopper, with a staged path

**Primary: self-hosted GraphHopper (open source).** It is the only candidate that has all three requirements at once: a native round-trip primitive, declarative per-request custom costing over data we control (via custom encoded values built into our own graph), and a permissive Apache 2.0 license. The concept document already anticipated "GraphHopper-class round-trip routing plus custom constraint scoring" (`research/04-synthesis/concept.md` section 5). The moat requirement decides this: hosted APIs cannot ingest our proprietary crossing and lighting data into their graphs, so any hosted primary would reduce Waypoint to commodity routing, exactly what the concept forbids.

**Staging.** Build the walking skeleton against the GraphHopper cloud free tier or a laptop-local instance (identical API), then stand up the production self-hosted instance before beta. This gives the fastest possible first demo without architectural throwaway.

**Fallback: Stadia Maps hosted Valhalla.** If self-hosting proves unmanageable at solo-founder scale, Stadia's hosted Valhalla plus `linear_cost_factors` (computing avoid/prefer geometries server-side from our context data and passing them per request) preserves a degraded version of the constraint moat at predictable cost, and their enterprise tier offers bespoke deployments where custom data could be negotiated. This is the escape hatch, not the plan. [inferred]

**Hosting cost estimates (self-hosted GraphHopper).** Basis: Hetzner cloud prices after their June 15, 2026 increase; a shared-vCPU CX-series 16 GB instance (CX43 class) costs about 16 EUR/month and 32 GB (CX53 class) about 29.49 EUR/month; dedicated-vCPU CCX23 (16 GB) is 85.99 EUR/month. [verified as to instance prices] (Hetzner price adjustment table, https://docs.hetzner.com/general/infrastructure-and-availability/price-adjustment/, and Northflank analysis, https://northflank.com/blog/hetzner-cloud-server-price-increases, accessed 2026-07-30). Graph memory scales with coverage area; launch coverage is metro/country extracts, not the planet. The MAU-to-cost mapping below is [inferred] from instance prices plus typical GraphHopper memory behavior; validate with a load test in the technical spike.

| Scale | Setup | Estimated monthly cost |
|---|---|---|
| 1k MAU (MVP, a few launch metros) | 1x 16 GB shared vCPU (graph plus API on one box), snapshots | 20 to 40 EUR |
| 10k MAU (US-wide or multi-country) | 2x 32 GB shared vCPU behind a load balancer, separate graph-build box run on demand | 90 to 160 EUR |
| 100k MAU (multi-region) | 4 to 6 dedicated vCPU 32 to 64 GB nodes, two regions, build pipeline, on-call reality | 800 to 2,000 EUR |

**License notes (OSM ODbL).** OSM data is ODbL: attribution plus share-alike on derivative databases. Routing instructions served to users are a Produced Work under the OSMF routing safe harbour and need attribution but not share-alike. The sharp edge for Waypoint: our derived context layers. If crossing graphs and lighting scores are computed *from OSM data* (adapting or enhancing it), that derived dataset is a Derivative Database, and publicly using it means we must make it (or the method to recreate it) available under ODbL on request. Mitigations: (a) keep independent-source layers (municipal lighting datasets, our own user-derived signals) as separate databases joined only at query time, which the license treats as a Collective Database not subject to share-alike; and (b) accept that OSM-derived layers (the crossing graph) may be publishable, since the moat also lives in the scoring models, personalization, and freshness, not solely in the static extract. Get counsel review of the layer boundaries before launch. [verified as to the license mechanics] (OSMF attribution guidelines including the routing safe harbour, https://osmfoundation.org/wiki/Licence/Attribution_Guidelines; OSMF licence FAQ on Derivative and Collective Databases, https://osmfoundation.org/wiki/Licence/Licence_and_Legal_FAQ; OSM wiki use cases, https://wiki.openstreetmap.org/wiki/License/Use_Cases; all accessed 2026-07-30) (the mitigation strategy is [inferred])

## 2. Data layers for the moat: build, buy, or derive

| Layer | Source | Build/buy/derive | Notes |
|---|---|---|---|
| Base road/path network | OSM | Buy (free, ODbL) | Commodity. Everyone has it. |
| Surface, footways, crossings | OSM tags | Derive | `surface=*`, `highway=footway/path`, `highway=crossing` nodes and `footway=crossing` ways are in the data; our derived crossing graph (crossings per km per edge) is the moat artifact. [verified as to tag existence; see lit discussion below for coverage caveats] |
| Lighting | OSM `lit=*` plus municipal open data | Derive | The core safety input. See detail below. |
| Elevation | AWS Terrain Tiles plus Copernicus GLO-30 | Buy (free, open) | See detail below. |
| Weather and heat | Apple WeatherKit primary | Buy | See detail below. |
| Populated-path and safety proxies | POI density, path class, daylight, later user-run density | Derive | No crime data at MVP. See ethics note. |

**OSM tag reality check.** The `lit=*` key is "de facto" status in the OSM wiki and is widely used (edited by 156,000+ mappers), but coverage is uneven: absence of the tag does not mean absence of lighting, and coverage quality varies enormously by city. The scoring model must treat `lit` as three-state (yes / no / unknown) and blend other signals (street lamp nodes via `highway=street_lamp`, road class, municipal datasets). This data-quality problem is exactly why a well-built lighting score is a moat and not a commodity: anyone can read the tag, few will do the fusion work. [verified as to tag status and usage; the coverage-unevenness characterization is [inferred] from the wiki's own guidance that unknown must be distinguished from unlit] (OSM wiki, Key:lit, https://wiki.openstreetmap.org/wiki/Key:lit; taginfo, https://taginfo.openstreetmap.org/keys/lit; both accessed 2026-07-30)

**Elevation.** Two free, commercially usable sources: (1) Terrain Tiles on AWS Open Data (the former Mapzen tiles): global bare-earth elevation tiles on S3, no AWS account required to read. (2) Copernicus GLO-30 DEM: 30 m global digital surface model under a free and open license that grants reproduction, distribution, and adaptation free of charge, with a required attribution notice (DLR and Airbus under Copernicus by the EU and ESA). Recommendation: Terrain Tiles for the graph-build pipeline (tiled, ready to consume), GLO-30 as the quality cross-check. Cost is S3 egress only, effectively zero at our scale if we cache tiles during builds. [verified] (AWS Open Data registry, Terrain Tiles, https://registry.opendata.aws/terrain-tiles/; Copernicus GLO-30 license PDF, https://documentation.dataspace.copernicus.eu/APIs/SentinelHub/Data/DEM/resources/license/License-COPDEM-30.pdf; Copernicus Data Space collection page with attribution text, https://dataspace.copernicus.eu/explore-data/data-collections/copernicus-contributing-missions/collections-description/COP-DEM; all accessed 2026-07-30)

**Weather.** Apple WeatherKit includes 500,000 API calls/month with the Apple Developer Program membership we already need; paid tiers start at $49.99/month for 1M calls and $249.99/month for 5M. Native Swift API on-device. [verified] (Apple, WeatherKit get started, https://developer.apple.com/weatherkit/get-started/, accessed 2026-07-30). Open-Meteo's free API is non-commercial only (10,000 calls/day); commercial use requires a paid subscription (Standard tier capped at 1M calls/month; prices not captured in this pass), data licensed CC BY 4.0 requiring attribution. [verified as to tiers and license; specific EUR prices [assumption] A5] (Open-Meteo pricing, https://open-meteo.com/en/pricing, and licence, https://open-meteo.com/en/licence, accessed 2026-07-30). Tomorrow.io free API tier allows only 500 requests/day; its docs page lists Team from $23/month and Business from $120/month but that page is flagged as years old, so treat those numbers as stale. [verified as to the 500/day free limit; paid tiers [assumption] A5] (Tomorrow.io free plan rate limits, https://support.tomorrow.io/hc/en-us/articles/20273728362644-Free-API-Plan-Rate-Limits; plan docs, https://docs.developer.tomorrow.io/docs/your-account; both accessed 2026-07-30). Recommendation: WeatherKit primary (free tier covers us far past 10k MAU at roughly 1 to 2 calls per generated route), Open-Meteo commercial as the server-side fallback since its API also serves the graph pipeline (historical heat exposure) without Apple dependency. Check the "safety-critical use" license question from the compliance doc's open questions before wiring weather into safety-adjacent copy.

**Pedestrian safety proxies: what we will and will not use.**
- Use: lighting score (above), path class and footway separation from OSM, POI and transit density as a populated-path proxy, daylight/civil twilight timing, and over time Waypoint's own completed-run density (our data, consented). [inferred approach]
- Do not use at MVP: open crime data. Reasons: (a) ethics and legal exposure: the compliance research explicitly flags that crime-data-driven steering may create discrimination or redlining exposure and is as much a fairness question as a legal one (`research/01-market/regulatory-compliance.md`, open questions); (b) comparability: crime datasets differ by jurisdiction in definitions, geography, and reporting bias, so a cross-city score would encode reporting artifacts; (c) product framing: we market "safety-aware" (lighting, populated paths), never "safe", and crime scoring pushes the product toward an implied guarantee it cannot honor. Revisit post-MVP with counsel and a fairness review if user research demands it. [inferred, and consistent with the locked concept's liability posture]
- Strava data is off the table for any model input: Strava's API agreement bans AI/ML ingestion of its data; Waypoint only exports completed runs to Strava (per the locked concept and `research/02-competitors/adjacent-platforms.md`). [verified in prior phase research]

## 3. iOS app layer

**Map rendering: SwiftUI plus MapKit.** MapKit is free with no usage-based pricing for native apps, first-party (no third-party SDK to audit under our Apple 5.1.3 and FTC posture), and renders custom polylines and overlays fine for a route-display app. Mapbox's Maps and Navigation SDKs are excellent but introduce metered pricing (Navigation SDK free tier is only 100 MAU on metered trips) and a third-party data flow to audit. Waypoint's map needs are modest (render a generated route, follow position along it); we do not need Mapbox's styling depth at v1. [verified as to Mapbox pricing, https://docs.mapbox.com/ios/navigation/guides/pricing/, accessed 2026-07-30; MapKit being free for native apps is long-standing Apple platform behavior, [verified] via Apple's MapKit documentation, https://developer.apple.com/documentation/mapkit/, accessed 2026-07-30; the sufficiency judgment is [inferred]]

**Turn-by-turn voice: build it, thin.** MapKit does not provide turn-by-turn guidance UI for arbitrary custom routes; guidance for a GraphHopper-generated polyline is ours to build: on-route position tracking, off-route detection, and spoken cues via AVSpeechSynthesizer from the instruction list GraphHopper returns. This is genuinely buildable at solo scale because running guidance is simpler than driving guidance (low speeds, no lane guidance, no live traffic). Evaluate Ferrostar (the open-source navigation SDK Stadia maintains, with Swift support) as an accelerator before writing from scratch. [inferred as to the build approach; Ferrostar's existence and FOSS status [verified], https://stadiamaps.com/products/routing-navigation/, accessed 2026-07-30]

**HealthKit and WorkoutKit.** HealthKit is the personalization backbone (readiness signals, training history) per the locked concept's HealthKit-first posture. WorkoutKit (iOS 17/watchOS 10 and later) lets Waypoint compose custom interval workouts, sync them to the Workout app on Apple Watch with user permission, schedule them, and query completion. This means v1 gets a credible Watch story without building a full watchOS app: Waypoint schedules the day's workout to the native Workout app, and the phone app runs voice guidance. [verified] (Apple, WWDC23 "Build custom workouts with WorkoutKit", https://developer.apple.com/videos/play/wwdc2023/10016/; WWDC24 update, https://developer.apple.com/videos/play/wwdc2024/10084/; WorkoutKit sample code, https://developer.apple.com/documentation/WorkoutKit/customizing-workouts-with-workoutkit; all accessed 2026-07-30)

**watchOS companion approach.** Phase v1.0: WorkoutKit-scheduled workouts plus phone-based voice guidance (phone stays pocketed, which is the actual user need per `pain-points.md`). Phase v1.x: a lightweight watchOS app for glanceable turn cues and haptics, reusing the guidance engine. A fully standalone watch experience (run without phone) is explicitly post-MVP; it roughly doubles the execution-surface work. [inferred sequencing]

**Coaching inference: on-device first via Apple's Foundation Models framework.** As of iOS 26 (and expanded at WWDC 2026), the Foundation Models framework gives native Swift access to an on-device ~3B parameter model (offline, no request limits, structured output via Generable, tool calling), plus a much larger Private Cloud Compute (PCC) model with a 32K context window and reasoning, available at no cloud API cost to App Store Small Business Program members with under 2M downloads. The framework now accepts third-party models behind the same API, so a server LLM remains a drop-in option later. [verified] (Apple, WWDC26 "What's new in the Foundation Models framework", https://developer.apple.com/videos/play/wwdc2026/241/; WWDC26 "Build with the new Apple Foundation Model on Private Cloud Compute", https://developer.apple.com/videos/play/wwdc2026/319/; WWDC26 Apple Intelligence guide, https://developer.apple.com/wwdc26/guides/apple-intelligence/; all accessed 2026-07-30)
- Architecture: the training-plan math (load progression, readiness adjustments) is deterministic code, not an LLM. The LLM's job is the explainable-reasoning surface ("why this route, why this workout") and natural-language adaptation, which the on-device model handles because we control the prompt tightly and the output is bounded. PCC is the upgrade path for long-context plan reviews. [inferred design]
- Privacy implication, and it is decisive: HealthKit-derived signals never leave the device for coaching. That collapses the GDPR Article 9 server-side processing surface, aligns with Apple 5.1.3, and satisfies the compliance checklist's on-device-by-default recommendation (`regulatory-compliance.md` checklist item 5). A server LLM for coaching would put special category health data on our servers and a model host's, requiring DPAs, a heavier DPIA, and a degraded-mode design for consent withdrawal. Avoid at MVP. [inferred from the verified compliance requirements]
- Fallback risk: Foundation Models requires Apple Intelligence eligible devices (roughly iPhone 15 Pro and later). Older devices get template-based (non-LLM) explanations rather than a server fallback, keeping the privacy posture uniform. [verified as to device eligibility being a framework constraint, per the WWDC sessions above; the fallback choice is [inferred]]

## 4. Backend

**Recommendation: Supabase (Postgres plus PostGIS) as the platform, one Hetzner VM for the routing engine, RevenueCat for entitlements.**

- **Supabase**: managed Postgres with auth, storage, and edge functions; Pro plan $25/month including a compute credit covering one Micro instance, 8 GB database, 100k MAU of auth, 250 GB egress. PostGIS and pgrouting ship as supported extensions. This is the pragmatic solo-founder choice: one vendor covers accounts, database, and API glue, and it is all standard Postgres underneath (no lock-in beyond Postgres itself, exportable any day). [verified] (Supabase pricing, https://supabase.com/pricing; supabase/postgres extension list including PostGIS and pgrouting, https://github.com/supabase/postgres; both accessed 2026-07-30)
- **Postgres plus PostGIS for the moat data: justified.** The proprietary context layers are inherently geospatial: per-edge lighting scores, crossing densities, surface overrides, privacy-zone geometries, and the pipeline that derives them from OSM extracts and municipal datasets. PostGIS gives spatial joins, indexing, and tile generation in SQL, and the graph-build pipeline reads from it to emit GraphHopper custom encoded values. A document store (Firebase) would force us to reimplement spatial operations in application code. The verdict: PostGIS is not just justified, it is the moat's workshop. [inferred, on verified PostGIS availability]
- **Route generation orchestration**: a thin API service colocated on the routing VM (or a Supabase edge function calling the routing VM) that: assembles constraints (user prefs from Postgres, weather from WeatherKit/Open-Meteo, daylight), builds the custom model JSON, calls GraphHopper, post-scores candidate loops (novelty vs personal history, safety score), and returns the winner with reasoning metadata. Keep it one process, boring and observable. [inferred design]
- **Subscriptions: RevenueCat over StoreKit 2 direct.** RevenueCat is free to $2,500 monthly tracked revenue, then 1% of MTR; it provides server-side entitlement checks, receipt validation, webhooks, and churn analytics out of the box. [verified] (RevenueCat pricing, https://www.revenuecat.com/pricing, and billing docs, https://www.revenuecat.com/docs/welcome/set-up-revenuecat/account-management, accessed 2026-07-30). StoreKit 2 direct is entirely viable and free, but rebuilding entitlement webhooks, cross-device state, and subscription analytics is weeks of solo-founder time spent on commodity plumbing; 1% of revenue is cheap insurance during the window where speed is a business requirement. RevenueCat processes purchase data, not health or location data, so the SDK audit surface is small; still execute a DPA per compliance checklist item 9. [inferred recommendation]
- **Telemetry**: privacy-first product analytics only, no ad tech and no cross-app tracking (Apple 5.1.3 posture, compliance checklist item 8). Prefer a privacy-focused vendor (for example TelemetryDeck or PostHog EU-hosted) or plain first-party events into Postgres at MVP scale; vendor selection needs its own audit and was not verified in this pass. [assumption] A6
- **Rejected alternatives.** Swift on server (Vapor): keeps one language, but the ecosystem for geospatial and payments tooling is thin and contractor availability is worse; not worth it for a thin orchestration layer. Firebase: no PostGIS, NoSQL is a poor fit for spatial moat data, and Apple 5.1.3's no-health-data-in-analytics posture makes the tight Google Analytics coupling a liability. Custom Node/Python on Fly.io/Railway/AWS: perfectly fine, but it re-implements auth and adds a second platform to operate; adopt only if Supabase limits bite. [inferred]

## 5. Privacy architecture

Where data lives, per the compliance doc's non-negotiables (privacy zones by default, private by default, on-device preference, no health data in iCloud per Apple guideline 5.1.3(ii)):

- **On-device only**: raw HealthKit data, readiness computation, coaching LLM inference, full-resolution GPS traces of completed runs, the user's true home location. HealthKit data is never written to our servers or to CloudKit. [design commitment, per verified Apple 5.1.3 and GDPR Article 9 obligations in `regulatory-compliance.md`]
- **Server, transient**: route generation requests need a start coordinate and constraint set. Mitigations: process in memory, do not persist raw start coordinates, log only coarse (truncated-precision) coordinates with a short TTL (default 30 days) for abuse and debugging, and treat the start point as sensitive end to end (the Strava lesson from the compliance research). [inferred design implementing verified requirements]
- **Server, durable**: account record, consent ledger (statement, timestamp, policy version per consent, per compliance checklist item 3), subscription entitlements, user preference weights (not health data), and privacy-zone geometries (needed server-side so route generation and any future sharing surface can enforce them before data leaves the trust boundary). Privacy zones are created during onboarding around home/work, applied at generation time (routes are jittered to start at the zone edge, never the true origin) and at export time (Strava export crops inside zones on-device before upload). Zone enforcement happens before data leaves the device or reaches shared surfaces, not as a display mask (compliance checklist item 1 implementation note). [inferred design implementing verified requirements]
- **Retention defaults**: completed-run history lives on device (and the user's own Strava if exported); server-side generated-route records keep only route geometry hashes and scores for novelty tracking, with raw geometries expiring after 90 days; account deletion cascades within statutory windows (checklist item 6). Exact schedule needs the DPIA pass. [assumption] A7
- **EU AI Act Article 50 hook**: coaching chat and AI-generated plans disclose AI at first interaction and carry a persistent "AI-generated" label in the UI, shipping in v1.0 since the obligation applies from August 2, 2026, before our launch. The disclosure copy and the classification memo (limited risk, not Annex III) come from the compliance research. [verified obligation, per `regulatory-compliance.md` section 4]

## 7. Recommendation summary

| Layer | Choice | Why | Monthly cost (MVP / 10k MAU) | Biggest risk |
|---|---|---|---|---|
| Routing engine | Self-hosted GraphHopper (Apache 2.0) | Only engine with native round_trip plus per-request custom cost models over data we control; hosted APIs cannot ingest moat data | $25 / $120 | Custom models are beta; node-level crossing penalties need Java work; ops burden on a solo founder |
| Moat data store | Supabase Postgres plus PostGIS | Spatial joins and pipeline workshop for crossing/lighting layers; one vendor for auth, DB, API | $25 / $40 | ODbL share-alike boundary on OSM-derived layers needs counsel sign-off |
| Elevation | AWS Terrain Tiles plus Copernicus GLO-30 | Free, open, commercially licensed, attribution only | $0 / $0 | Tile quality varies by region; cross-check needed |
| Weather | Apple WeatherKit (Open-Meteo commercial fallback) | 500k calls/month free with membership we already pay for; native Swift | $0 / $0 to $50 | Apple dependency; server-side pipeline needs the fallback anyway |
| Map and navigation | SwiftUI plus MapKit, custom voice guidance (evaluate Ferrostar) | Free, first-party, no third-party SDK audit; running guidance is buildable | $0 / $0 | Guidance engine is real engineering; underestimating it slips the MVP |
| Watch | WorkoutKit sync to native Workout app, watch app in v1.x | Credible Watch story with a fraction of the build | $0 / $0 | Perceived as thin vs competitors with full watch apps |
| Coaching AI | On-device Apple Foundation Models (PCC for long context) | Free, offline, health data never leaves device, collapses Article 9 surface | $0 / $0 | Requires Apple Intelligence devices; older iPhones get template explanations |
| Subscriptions | Apple IAP via RevenueCat | Entitlement infra for 1% of revenue; billing-law mechanics delegated to Apple | $0 / $65 | 1% forever; migration off is work later |
| Backend glue | Thin API on routing VM plus Supabase functions | One boring process, observable, cheap | included / included | Single-VM blast radius at MVP (acceptable, snapshot-restore) |

**Build order (walking skeleton first).** 1) GraphHopper local with foot profile, round_trip, and a first custom model using stock encoded values (surface, road class): proves the loop primitive week one. 2) iOS app: MapKit render of a generated loop from current location with distance input: the demo moment. 3) Voice guidance engine on the generated polyline. 4) HealthKit read plus WorkoutKit scheduling. 5) First moat layer (lighting score in PostGIS, exported as a custom encoded value into the graph build): this is when Waypoint stops being commodity. 6) Accounts, privacy zones, RevenueCat, paywall. Constraint data deepens forever after; the skeleton must not wait for it.

**Founder decisions flagged (recommended answers included):**

1. **Commit to self-hosted GraphHopper now, or prototype on the cloud API first?** Recommended: prototype the skeleton on the free cloud tier or laptop-local for weeks 1 to 4, but provision the production VM before any beta user touches the app, because the moat data cannot ever run on the hosted API and late migration re-tests everything.
2. **RevenueCat or StoreKit 2 direct?** Recommended: RevenueCat. The 1% fee buys back weeks of commodity plumbing during the competitive window; revisit only past roughly $50k MTR when the fee approaches a contractor's cost.
3. **MapKit plus custom voice guidance, or Mapbox Navigation SDK?** Recommended: MapKit plus custom guidance, with a two-day spike on Ferrostar before writing the guidance engine from scratch. Mapbox is the fallback if the spike shows guidance is harder than assessed, accepted with its MAU pricing and SDK audit cost.
